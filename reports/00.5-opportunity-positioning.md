## 1. Purpose

This report freezes the opportunity, prior-art, interoperability, naming, Hedera-integration, and public-claim position before the IRP-1 normative protocol is committed.

The public opportunity is **not** generic "AI receipts". The viable wedge is an independently verifiable action-correspondence protocol that connects:

1. declared observation boundary;
2. declared interpretation and exact intended action;
3. deterministic policy replay;
4. explicit human-approval state;
5. pre-action authorization commitment;
6. observed post-action outcome;
7. independent correspondence verdict;
8. optional Hedera consensus ordering/timestamp evidence.

## 3. Hedera Ecosystem Recheck

Hedera Agent Kit v4, announced in May 2026, provides modular packages, explicit plugin selection, deterministic policies, and hookable lifecycle stages around tool execution. This strengthens the integration opportunity and removes any requirement for IRP-1 to invent a replacement agent runtime.

IRP-1 should remain an independent protocol/verifier first, then integrate with the Agent Kit lifecycle as a plugin/adapter.

Hedera Consensus Service remains the intended independent ordering/timestamp substrate for minimized W2 and W3 commitments. Mirror Node is the independent retrieval surface. Hedera is **not** treated as a semantic-truth authority.

## 4. SCITT / Adjacent Standards Recheck

Current SCITT-related work materially overlaps broad receipt and authorization concepts. Relevant active Internet-Drafts include:

- `draft-noa-scitt-ai-agent-receipt-01` — AI-Agent Action Receipts;
- `draft-mih-scitt-agent-action-capsule-02` — Agent Action Capsule;
- `draft-munoz-scitt-permit-profile-01` — Pre-Execution AI Action Authorization Records / Permit;
- refusal-event, selective-disclosure, provenance-binding, composite-evidence, and related profiles.

These documents are works in progress. Their presence is relevant prior art and standards context; it does not mean every proposal is an adopted IETF standard.

The Permit profile already binds a pre-execution policy decision to canonical request bytes and defines a paired Closure Record. It explicitly does not define a policy language or policy-evaluation engine.

Therefore IRP-1 MUST NOT claim invention of the generic concepts of signed agent receipts, pre-execution authorization records, or authorization-to-dispatch binding.

## 6. Canonicalization Decision — FROZEN

IRP-1 v1 uses **RFC 8785 — JSON Canonicalization Scheme (JCS)** as the normative canonical JSON algorithm.

IRP-1 additionally restricts accepted protocol values to an **I-JSON-compatible subset** and rejects unsupported runtime values before JCS serialization.

Requirements:

- deterministic canonical JSON output;
- no bespoke serialization novelty;
- fixed cross-implementation compatibility vectors;
- unsupported values rejected rather than silently coerced;
- incompatible canonicalization changes require a new schema/version;
- historical receipts are never silently migrated.

## 7. Signature / Digest / Consensus Decision — FROZEN

IRP-1 separates three evidence layers:

1. **Receipt digest** — required for IRP-1 v1 integrity and chaining.
2. **Issuer / approver signature** — reserved as a compatible authentication layer; it may be deferred in the v0.1 public proof if the limitation is explicit.
3. **Consensus anchor** — optional for general IRP-1 use, but required for the Hedera public-proof profile.

A SHA-256 digest does not by itself authenticate the real-world identity of an actor or approver.

IRP-1 should reuse established signature/transparency structures where appropriate instead of inventing a proprietary signature envelope without need.

## 8. SCITT Interoperability Decision — FROZEN

IRP-1 v1 remains independently implementable and independently verifiable.

A future SCITT mapping/export profile is an interoperability seam, not part of the initial public proof and not a replacement for SCITT.

Target composition:

```text
IRP-native receipts
  ├─ Hedera anchor profile
  ├─ future SCITT export/profile

```

## 9. Receiver-Side Evidence Boundary

Receiver-attested work such as *Notarized Agents* highlights a residual trust boundary: a compromised observation/execution host may fabricate what it claims to have observed.

IRP-1 v1 does not claim to solve that problem universally. Future strengthening may compose with receiver-signed evidence, external service attestations, hardware-backed evidence, or trusted-execution attestations.
